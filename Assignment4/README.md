# Task 1 – GUI Design Review: Diagnose & Repair Fee-Payment Window

## Task 1.1 – Diagnose the Design
1. **No Separation of Interface and Logic:** SQL queries, JDBC connections, and sleep delays are embedded directly inside `FeeWindow.actionPerformed()`[cite: 46]. Any database schema change forces edits to the UI class, and business rules cannot be unit-tested without launching a GUI[cite: 46].
2. **Reference Comparison (`==`) on Action Command:** `e.getActionCommand() == "Pay"` compares `String` object references instead of content (`.equals()`)[cite: 46]. If a button label comes from a dynamic resource bundle or localization string, the condition fails silently and clears the user's input via the `else` branch[cite: 46].
3. **Missing Input Validation:** `Double.parseDouble(amount.getText())` throws an uncaught `NumberFormatException` on empty or alphabetic input, and negative/zero amounts are accepted without rejection[cite: 47].
4. **Blocking the Event-Dispatch Thread (EDT):** Running `DriverManager.getConnection()`, SQL execution, and `Thread.sleep(3000)` directly on the EDT freezes the entire window for 3+ seconds—clicks, repaints, and window close buttons become completely unresponsive[cite: 47].
5. **Unhandled Receipt Button & Destructive Else Branch:** Clicking `Receipt` falls into the `else` block, wiping out `regNo` and `amount` instead of generating a receipt[cite: 47].
6. **SQL Injection & Resource Leaks:** String concatenation allows SQL injection; JDBC `Connection` and `Statement` are never closed; `windowClosing` is unhandled; checked `SQLException` and `InterruptedException` are unhandled; feedback goes only to `System.out` instead of a UI label/dialog[cite: 47].

## Task 1.3 – Design Defence & Complexity Analysis
* **Design Defence:** Separating `FeeService` from `FeePaymentApp` isolates validation and JDBC persistence from Swing components[cite: 47, 50]. Developers can write automated JUnit tests against `FeeService.processPayment()` directly without instantiating windows or simulating button clicks[cite: 50]. Dedicated listeners eliminate fragile if-else string branching, making it trivial to add new buttons (such as `Receipt`) without breaking existing actions[cite: 50]. Moving database execution onto `SwingWorker` keeps the Event-Dispatch Thread responsive during network latency, while try-with-resources and `PreparedStatement` prevent connection leaks and SQL injection[cite: 50, 51].
* **Alternative Concept & Complexity:** With one shared listener using an if-else chain across $k$ buttons, dispatching an event performs up to $O(k)$ string comparisons in the worst case while allocating $O(1)$ listener object[cite: 51]. Assigning each of the $k$ buttons its own dedicated listener (or Swing `Action`) dispatches directly via the button's listener list in $O(1)$ time (zero string comparisons), at the cost of $O(k)$ lightweight listener instances[cite: 51].
